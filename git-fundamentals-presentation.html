Part 01 · Fundamentals

Git vs. GitHub

Git
→ Version control software on your computer
→ Works offline — no internet needed
→ Command-line based, with GUI alternatives (GitHub Desktop, GitKraken, SourceTree)
GitHub
→ Website that hosts Git repositories in the cloud
→ Web interface for viewing code and changes
→ Collaboration tools — pull requests, issues, comments
→ Social coding — followers, stars, forks

Part 01 · Fundamentals

What is a repository?

Where Git stores your project’s full history — every commit, branch, and change.
git init # turn an existing folder into a repository
git clone <url> # download a copy of one that already exists
🏆 Golden rule: always run git status before git init. If it errors, you’re safely outside a repo.

What’s inside a commit?

A commit is a permanent snapshot of your files, linked to the one right before it.

📸 A snapshot of all your files and folders at that point in time — Git calls this a tree.

Part 01 · Fundamentals

Trees reuse unchanged files

When you commit again, only changed files get a new blob — everything else is reused.
Commit 1
🌳 tree
📄 index.html
📄 styles.css
Commit 2
🌳 tree
📄 index.html
📄 styles.css
index.html unchanged — both commits point to the exact same blob
styles.css changed — commit 2 points to a new blob with the updated content
Part 01 · Fundamentals

From edit to commit

Your changes move through three places before they become permanent.
Working directory — the files you see and edit
Staging area — what git add prepares for the next commit
Repository — the permanent history git commit writes to
git status # what changed?
git add <file> # stage it (or . for all)
git commit -m "message" # turn the staged snapshot into a commit
git push # send your commits to GitHub

Part 01 · Fundamentals

Writing good commits

Small & focused — one logical change per commit
Commit often — don’t wait for "perfect", save progress as you go
Meaningful messages — describe what changed and why, not just "fix"
Imperative mood — "Add search filter", not "Added" or "Adding"
Keep it working — avoid committing code that breaks the build
Separate concerns — don’t mix unrelated changes in one commit
feat: add search filter to product list
fix: correct off-by-one error in pagination
# optional: Conventional Commits format — type: description

Part 02 · Collaboration

What is a merge conflict?

Git can’t automatically decide how to combine changes — usually because two people edited the same lines.
Two branches changed the same part of a file
Git pauses the merge and asks you to decide
It’s normal — not a sign something is broken
Part 02 · Collaboration

Anatomy of a conflict

<<<<<<< HEAD
Local text kept here
=======
Incoming text from the other branch
>>>>>>> feature-branch
Git marks both versions directly in the file — you decide what stays.
Part 02 · Collaboration

Resolving a conflict

1
Open the file(s) marked as conflicted (git status shows them)
2
Decide what the final content should be — keep, combine, or discard
3
Remove the <<<<<<< ======= >>>>>>> markers
4
git add <file> to mark it as resolved
5
git commit to complete the merge
Part 02 · Collaboration

Two people, one branch

Working on the same branch at the same time multiplies the chance of conflicts — and confusion.
Risky
→ Both push at the same time — the second push is rejected
→ Force-pushing to "fix" it can erase a teammate’s work
→ Unclear who’s responsible for which part
Better
→ git pull before you start working, and before you push
→ Split work into small, separate branches per feature/person
→ Communicate — say what file or section you’re touching

Part 02 · Collaboration

Collaboration golden rules

Pull before you push, and often
Small, frequent commits with clear messages
One feature/person per branch when possible
Review each other’s PRs before merging
Communicate — don’t let Git replace conversation
